# core-mcp-engine: MCP-движок — запуск проекта как MCP-сервера

**Профиль:** normal

## Цель

Дать `@clapp` второй способ запуска приложения — не только CLI, но и MCP-сервер. Движок поверх
того же набора плагинов-команд должен отдавать команды проекта MCP-клиенту и обслуживать вызовы
через SDK `@modelcontextprotocol/server`. Работа идёт на базе текущей заготовки
`packages/core/src/engines/mcp/`, которая сейчас не компилируется, не подключена к сборке и
использует непоставленные зависимости.

Ключевое решение по модели команд (уточнено пользователем): команда проекта бывает ровно трёх
видов, и каждый вид отображается на свою поверхность MCP:

| вид команды | смысл | поверхность MCP |
|---|---|---|
| запрос информации | чтение данных о проекте/состоянии, без побочных эффектов | **Resources** |
| выполнение действия | действие в проекте в контексте workflow (есть побочные эффекты) | **Tools** |
| команда ИИ | отправка конкретной инструкции/команды модели вместе с аргументами | **Prompts** |

Поэтому первый шаг работы — дать автору команды возможность указать её вид в определении плагина
(подробности — § 3.0 `_concept.md`).

Задача — в общих чертах: конкретные требования, объём MVP и декомпозиция `_todo.yml` выводятся
после ответов на открытые вопросы, собранные в `_concept.md`. Этот файл — единственный источник
контекста задачи: детали SDK, разбор заготовки, предлагаемая архитектура, фазы и риски лежат там.

## Требования

Решения фазы 0 (транспорт stdio, движок в ядре, три поверхности, отдельный bin, свой конвейер
исполнения, MCP-набор форматтеров) — в `_concept.md` § 6.1 и § 6.3.

1. **Вид команды в определении плагина** (выполнено в фазе 1). `IPluginCommandDefinition`
   (`@clapp/common`, `packages/common/src/types/plugin.ts`) получил обязательное поле `kind` с тремя
   значениями (`resource` | `tool` | `prompt`) плюс маркер узла-группы `group`; константы, типы и
   экспорт из публичного API — `packages/common/src/constants/plugin-types.ts`; существующие
   определения команд `packages/ai/plugins/commands/**` обновлены.
2. Работать по концепции `packages/core/.opencode/tasks/core-mcp-engine/_concept.md`: решения фазы 0
   зафиксированы (§ 6.1), конвенции генерации MCP-данных — § 6.2, итоговый облик движка — § 6.3.
3. **Изменения не синхронизировать с текущей реализацией `CliEngine`.** CLI-движок и его конвейер
   исполнения не трогаем; доработка CLI-движка, общий `CommandExecutor` и приёмник вывода —
   отдельная работа позже.
4. Реализовать движок **в ядре** (`packages/core/src/engines/mcp/**`), совместимый с `IEngine` —
   вторую (после `CliEngine`) реализацию, выбираемую в точке входа через `bootstrapApp`/
   `ENGINE_TOKEN` и запускаемую **отдельным bin** (подкоманду `mcp` не делаем).
5. Транспорт MVP — **stdio** (`serveStdio`); фабрика `McpServerFactory` создаёт `McpServer` на
   соединение, сервер-инфо (`name`/`version`/`instructions`) берётся из `IAppConfig`.
6. Отдавать команды проекта во все три поверхности MCP в соответствии с их видом: `tool` →
   `registerTool` (схема аргументов из `ICommandConfig`), `resource` → `registerResource`
   (URI/шаблон), `prompt` → `registerPrompt` (аргументы и сообщения); `group` не экспонируется и
   служит префиксом пути в имени сущности; имена вложенных команд — путь через `/` (`board/list`).
   Данные сущностей генерируются из определения команды по конвенциям § 6.2 `_concept.md` (имя,
   `title` ← `label`, `description`, схема аргументов через `fromJsonSchema`, URI `clapp://<путь>`
   или шаблон `clapp://<путь>{?arg}`, `mimeType text/plain`, `annotations` по виду); отдельный блок
   метаданных в определении не вводим. Для проверки поверхности `prompt` в задаче добавляется одна
   простая промпт-команда (чисто для тестов — в `packages/ai` нет ни одной команды этого вида).
7. Исполнение вызова — **собственный конвейер движка** (события `command:start`/`arguments`/`run`/
   `end`/`error` → `getArguments` → `action`), без общего с CLI executor'а (отложен).
8. Результат команды — как содержимое ответа (текстовый блок + структурированные данные при наличии),
   ошибки — как результат с `isError`, без записи в stdout и без падения соединения; отладочный вывод
   — только в stderr. Команды без `formatter` (печатают сами: `board/list`, `board/next`,
   `skill-add`) в MCP **не экспонируются**, о пропуске — предупреждение в stderr; сами команды
   проекта в этой задаче не трогаем. Схему вывода (`outputSchema`/`structuredContent`) в MVP не
   отдаём — только текстовый `content`.
9. Рендер текста — **отдельный formatter PluginManager для MCP** (В5): своя константа типа плагина,
   свой DI-токен, свой набор discovery-паттернов и свой набор плагинов для stdio (без ANSI, текст для
   канала протокола); идентификаторы у команд остаются прежними (`formatter: 'table'` и т.д.),
   резолв идёт в наборе MCP. Форматтер **обязателен**: если MCP-плагин для используемого
   идентификатора не зарегистрирован — ошибка с понятным сообщением, фолбэка на CLI-форматтеры нет.
10. Довести заготовку до рабочего состояния: компилируемость, реэкспорт из публичного API, корректные
    зависимости и конфигурация движка (`IAppConfig.engine`: тип опций и дефолт, сейчас поле не задано).
11. **Живая проверка прототипа в рамках задачи**: запустить движок (tsx) по stdio и убедиться через
    MCP-клиент (скрипт-проверка в `tmp/`), что видны и корректно вызываются сущности всех трёх
    поверхностей, ошибки приходят как `isError`, stdout не засоряется; результаты и отклонения
    зафиксировать в `_reports.yml`. Коммитируемые тесты (in-memory клиент по трём поверхностям) и
    документация в задачу не входят — они отложены в релизные пункты `г14`/`б12`.

## Критерии готовности

- Решения фазы 0 зафиксированы в `_concept.md` (§ 6.1–6.3), открытых вопросов нет; требования и
  объём соответствуют им.
- Поле вида команды добавлено в определение плагина, экспортируется из публичного API и описано в
  документации/концепции; существующие определения команд обновлены.
- MCP-движок собирается и запускается отдельным bin по stdio: MCP-клиент видит `tools`, `resources`
  и `prompts`, соответствующие командам проекта (по их видам), и получает корректные результаты;
  ошибки приходят как `isError`, stdout не засоряется.
- Живая проверка прототипа выполнена (все три поверхности по stdio), результаты зафиксированы в
  `_reports.yml`; коммитируемые тесты и документация — в релизных пунктах `г14`/`б12`.
- `_todo.yml` декомпозирован по итоговому объёму и полностью закрыт.

## Вне рамок

- **Правки команд проекта**: `board/list`, `board/next`, `skill-add` и прочие команды, печатающие
  сами, в этой задаче не трогаем — их перевод на контракт «данные + `formatter`» отложен (фаза 3

  промпт-команда, добавляемая для проверки поверхности `prompt`.
