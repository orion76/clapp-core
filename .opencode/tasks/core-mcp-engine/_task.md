# core-mcp-engine: MCP-движок — запуск проекта как MCP-сервера

**Профиль:** normal

## Цель

Дать `@clapp` второй способ запуска приложения — не только CLI, но и MCP-сервер. Движок поверх
того же набора плагинов-команд должен отдавать команды проекта MCP-клиенту и обслуживать вызовы
через SDK `@modelcontextprotocol/server`. Работа идёт на базе текущей заготовки
`packages/core/src/engines/mcp/`, которая сейчас не компилируется, не подключена к сборке и
использует непоставленные зависимости.

Ключевое решение по модели команд (уточнено пользователем): команда проекта бывает ровно трёх
видов, и каждый вид отображается на свою поверхность MCP:

| вид команды | смысл | поверхность MCP |
|---|---|---|
| запрос информации | чтение данных о проекте/состоянии, без побочных эффектов | **Resources** |
| выполнение действия | действие в проекте в контексте workflow (есть побочные эффекты) | **Tools** |
| команда ИИ | отправка конкретной инструкции/команды модели вместе с аргументами | **Prompts** |

Поэтому первый шаг работы — дать автору команды возможность указать её вид в определении плагина
(подробности — § 3.0 `_concept.md`).

Задача — в общих чертах: конкретные требования, объём MVP и декомпозиция `_todo.yml` выводятся
после ответов на открытые вопросы, собранные в `_concept.md`. Этот файл — единственный источник
контекста задачи: детали SDK, разбор заготовки, предлагаемая архитектура, фазы и риски лежат там.

## Требования

1. **Вид команды в определении плагина.** Добавить в `IPluginCommandDefinition` (`@clapp/common`,
   `packages/common/src/types/plugin.ts`) обязательное поле вида команды (`kind`) с тремя
   допустимыми значениями (`resource` | `tool` | `prompt`, соответствующими MCP Resources / Tools /
   Prompts из таблицы выше) плюс маркер узла-группы (контейнер не отображается на MCP); значения —
   строковые константы в стиле `packages/common/src/constants/plugin-types.ts`, типы и константы
   экспортируются из публичного API `@clapp/common`. Поле обязательно и в авторском определении
   (`IPluginCommandDefinitionData`), поэтому все существующие определения команд (`packages/ai/
   plugins/commands/**`, 7 файлов) обновляются в этой же задаче. Итоговые решения — § 3.0
   `_concept.md`.
2. Работать по концепции `packages/core/.opencode/tasks/core-mcp-engine/_concept.md`: получить от
   пользователя ответы на её открытые вопросы и зафиксировать ответы в самой концепции.
3. **Изменения не синхронизировать с текущей реализацией `CliEngine`.** CLI-движок и его конвейер
   исполнения на этом этапе не трогаем (в том числе ради корректной работы существующих команд);
   доработка CLI-движка под три вида команд и общий executor — отдельная работа позже, по
   отдельному решению.
4. Реализовать движок, совместимый с `IEngine`, — вторую (после `CliEngine`) реализацию, выбираемую
   в точке входа хоста через существующий механизм `bootstrapApp`/`ENGINE_TOKEN`.
5. Отдавать команды проекта в MCP в соответствии с их видом: `resource` → чтение данных как ресурс,
   `tool` → вызов действия, `prompt` → получение сообщений для модели. Вызов идёт через тот же путь
   исполнения, что и в CLI (события `command:start`/`arguments`/`run`/`end`/`error`, `getArguments`,
   `action`).
6. Возвращать результат команды MCP-клиенту как содержимое ответа (текстовый блок + структурированные
   данные при наличии), а ошибки — как результат с `isError`, без записи в stdout и без падения
   соединения; отладочный вывод — только в stderr.
7. Переиспользовать существующие плагины-форматтеры для текстового представления результата.
8. Довести заготовку до рабочего состояния: компилируемость, реэкспорт из публичного API, корректные
   зависимости и конфигурация движка (`IAppConfig.engine`) вместо текущего нерабочего черновика.
9. Проверять работу автоматически: интеграционный тест через in-memory транспорт SDK с клиентом
   `@modelcontextprotocol/client` (список и вызов инструментов) и smoke-запуск по выбранному
   транспорту.

## Критерии готовности

- Ответы на открытые вопросы концепции получены и зафиксированы в `_concept.md`; требования и объём
  приведены в соответствие с ними.
- Поле вида команды добавлено в определение плагина, экспортируется из публичного API и описано в
  документации/концепции; существующие определения команд не ломаются либо осознанно обновлены.
- MCP-движок собирается и запускается: MCP-клиент видит сущности, соответствующие командам проекта
  (по их видам), и получает корректные результаты; ошибки приходят как `isError`, stdout не
  засоряется.
- Проверки выполняются автоматически (in-memory тест + smoke); для профиля `full` — сборка, тесты и
  typecheck зелёные.
- `_todo.yml` декомпозирован по итоговому объёму и полностью закрыт.
